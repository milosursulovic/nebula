​NEBULA​
​Distributed Cloud Infrastructure Platform in Go​
​Project Type​

​Senior-level backend / distributed systems / infrastructure engineering project.​

​Primary Goal​

​Build a miniature cloud infrastructure platform capable of managing compute nodes,​
 ​virtual machines, networks, storage, resource allocation, scheduling, asynchronous jobs,​
  ​and infrastructure agents.​

​NEBULA should behave conceptually like a simplified combination of:​

   ​●​               ​AWS EC2​
    ​●​               ​OpenStack​
     ​●​               ​Kubernetes control-plane concepts​
      ​●​               ​HashiCorp Nomad​
       ​●​               ​Proxmox​

​The purpose is not to build a production cloud provider.​

​The purpose is to build a serious distributed system that demonstrates understanding of:​

   ​●​               ​Go​
    ​●​               ​concurrency​
     ​●​               ​distributed systems​
      ​●​               ​scheduling​
       ​●​               ​networking​
        ​●​               ​Linux​
         ​●​               ​virtualization​
          ​●​               ​databases​
           ​●​               ​message queues​
            ​●​               ​fault tolerance​
             ​●​               ​observability​
              ​●​               ​security​
               ​●​               ​infrastructure automation​

​16. Resource Reservation​
​This is one of the most important concurrency problems in NEBULA.​

​Suppose a node has:​

​16 CPU​

​32 GB RAM​



​and 100 requests arrive simultaneously.​

​You must never end up with:​

​available_cpu = -12​



​Use transactional resource reservation.​

​Conceptually:​

​AVAILABLE​

  ​↓​

​RESERVED​

  ​↓​

​ALLOCATED​



​On failure:​

​RESERVED​
  ​↓​

​AVAILABLE​




​17. Database Concurrency​
​Use PostgreSQL transactions.​

​For critical resources use:​

    ​●​ ​row-level locks​
     ​●​ ​optimistic locking​
      ​●​ ​atomic updates​

​You should eventually experiment with both:​

​SELECT ... FOR UPDATE​



​and optimistic concurrency.​

​For optimistic locking, maintain a version field.​

​Example:​

​compute_nodes.version​



​If two schedulers attempt to reserve the same node:​

​Scheduler A → version 10​

​Scheduler B → version 10​



​A succeeds → version 11​
​B fails because version changed​



​B must retry scheduling.​




​18. Scheduler​
​Create:​

​type Scheduler interface {​

      ​Schedule(ctx context.Context, req ResourceRequest) (*Node, error)​

​}​



​Implement several strategies.​

​First Fit​

​Choose the first node with enough resources.​

​Best Fit​

​Choose the node with the smallest remaining capacity after allocation.​

​Least Loaded​

​Choose the node with the lowest load.​

​Weighted Scheduler​

​Combine:​

​CPU availability​

​RAM availability​

​disk availability​

​system load​
​number of instances​

​network capacity​



​Example:​

​score =​

  ​cpu_score * 0.30 +​

  ​memory_score * 0.30 +​

  ​disk_score * 0.15 +​

  ​load_score * 0.15 +​

  ​instance_score * 0.10​



​Make the strategy configurable.​

        ​↓​

        ​↓​
​mark published​

​24. Retry System​

​attempt 2 → 2 seconds​

​After maximum attempts:​

​26. Saga / Compensation​
​Instance provisioning is a multi-step distributed workflow.​

​Example:​

​Reserve resources​

    ​↓​

​Create disk​

    ​↓​

​Create network​

    ​↓​

​Create VM​

    ​↓​

​Start VM​

    ​↓​

​RUNNING​

​You must compensate:​

​Delete network​

​Delete disk​

​Release resources​
​The workflow therefore becomes:​

         ​Provision Instance​
